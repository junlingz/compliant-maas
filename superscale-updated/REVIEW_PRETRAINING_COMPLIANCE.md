- 需求基线：`../MaaS标书.docx` 中 `1.3.2.5.1 大规模预训练框架`，截止 `1.3.2.5.2` 前
- 审查角色：标书合规审查
- 审查日期：2026-07-30
- 初审结论：**不通过，存在 1 项 P0、9 项 P1、2 项 P2；结构映射完整，但不能据此认定功能完整覆盖**
- 整改复审结论：**仍不通过；已关闭 4 项 P1、1 项 P2，仍开放 1 项 P0、5 项 P1、1 项 P2**

## 一、审查口径

本次采用四层证据链，不把“出现条款文字”直接视为“功能已覆盖”：

1. **需求层**：直接解析标书目标段落，核对 8 个模块、39 个能力组、143 个功能条目、119 个细分交互。
2. **追溯层**：核对矩阵中的条款号、名称、页面路径、控件、交互反馈是否与实际页面一致。
3. **页面层**：逐个进入 8 个模块和 39 个能力组，检查是否存在与条款语义相符的专属工作台，而非仅有说明卡片。
4. **交互层**：实际运行页面并操作表单、筛选、任务控制、上传、导出、拓扑、监控、流程编排、部署等控件；只有产生对应状态变化、结果视图或可验证下载物才算实现。

运行检查结果：现有 `scripts/qa-prototype.mjs` 可通过，浏览器控制台无错误；但该脚本只验证每个能力组存在标题和要求卡片，没有验证条款要求的业务状态变化，因此不能作为完整合规证明。

### 2.2 严格功能覆盖

“部分覆盖”表示页面已有相关工作台，但至少一个标书明确要求的控件、状态或结果不存在；“高风险错配”表示页面主体与该能力组语义不符，主要依赖右侧条款说明卡声称覆盖。

| 模块 | 能力组 | 严格通过 | 部分覆盖 | 高风险错配 |
|---|---:|---:|---:|---:|
| 自回归预训练框架 | 6 | 0 | 5 | 1 |
| 序列到序列预训练框架 | 6 | 0 | 5 | 1 |

| 有监督的微调框架 | 6 | 0 | 6 | 0 |
| 强化学习框架 | 3 | 0 | 3 | 0 |

## 三、P0 问题

### P0-01：追溯矩阵把统一说明抽屉当作 262 个条款的实际功能落点

- **条款范围**：8 个模块下全部 143 个功能条目及 119 个细分交互，代表条款包括 `1.3.2.5.1.4.1.3.2`、`1.3.2.5.1.4.4.1.1#3`、`1.3.2.5.1.4.7.6.1#1`、`1.3.2.5.1.4.8.2.4#3`。
- **证据**：
  - `requirements-matrix-pretraining.md` 的功能条目统一写为“主工作台 + 右侧能力核验卡”，细分交互统一写为“能力核验标签 / 对应表单、列表、图表或操作按钮”，没有给出唯一控件 ID 或可验证状态。
  - 页面中所有功能“体验”按钮均调用同一个 `openDrawer`；所有细分项也只打开要求说明抽屉。
  - 抽屉中的“执行交互演示”统一触发 `simulateRequirement`，只显示“输入、状态与反馈链路正常”的 Toast，不执行条款对应业务动作。
  - 实测 39 个能力组均有要求卡，但这只能证明条款文本被展示，不能证明功能存在。
- **影响**：当前“100% 映射”“已覆盖”及自检通过结论不具备验收效力，会直接导致投标演示时被认定为以说明代替功能。
- **整改建议**：
  1. 每一条功能/细分交互必须绑定真实业务控件的唯一 `data-req-id`，矩阵记录具体页签、控件名称、前置输入、操作、预期状态和结果。
  2. 删除统一的“模拟已通过”逻辑；未实现项标记为“未覆盖”或“部分覆盖”。
  3. 增加自动化逐条验收：点击真实控件后验证 DOM 状态变化、表格行变化、图表序列变化、任务状态变化或下载文件类型。
  4. 在全部 P1 问题关闭前，不得显示“100% 映射”或“完整性自检通过”。

## 四、P1 问题

### P1-01：自回归核心配置、监控与自动化评估不满足显式交互要求

- **条款号**：`1.3.2.5.1.4.1.1.1`—`.1.1.5`、`.1.3.1`—`.1.3.4`、`.1.4.1`—`.1.4.4`。
- **证据**：
  - 选择“MoE 稀疏专家”后，页面未出现专家数量、路由策略、稀疏激活配置，模型摘要仍固定为 `7.62B / 62.4 GB`。
  - 数据集只有一个下拉框和通用上传按钮，没有“内置/自定义”分支、样本量、文本总长度、编码校验结果。
  - 监控页无“配置”入口、无指标勾选、无历史任务下拉；折线图路径静态不变，只有 KPI 数字和日志文本变化。
  - “自动化模型评估”页错误复用了训练配置表单；不存在困惑度/流畅度/逻辑一致性选择、评估频率、自动暂停过程、独立报告、样例对比、PDF/CSV 导出。
  - 提交任务弹窗成功后不会自动跳转到模块内训练监控页。
- **整改建议**：为核心训练、监控和自动评估建立三套专属状态模型；实现 MoE 动态参数、数据校验统计、可选实时曲线与历史回放、评估执行状态机、报告/样例视图及 PDF/CSV 下载。

### P1-02：序列到序列训练和评估仍是自回归通用表单

- **条款号**：`1.3.2.5.1.4.2.1.1`—`.2.1.4`、`.2.2.3`、`.2.3.1`—`.2.3.3`。
- **证据**：
  - 核心页没有编码器/解码器层数、隐藏单元数、注意力机制的独立配置，也没有拖拽架构。
  - 自定义平行语料只提供一次通用上传，未分别接收 `src.txt`、`tgt.txt`，未显示句子对齐、语料规模、词表大小。
  - 模型详情没有网络层数、参数量、注意力头数专属视图。
  - 自动化评估页复用训练表单，不存在 BLEU/ROUGE、评估数据路径/频率、源文本—生成文本—标签对比、PDF/CSV 导出。
- **整改建议**：增加 Encoder/Decoder 双栏配置和结构摘要；实现双文件上传及对齐校验；增加架构详情；建立 Seq2Seq 专属评估页。

### P1-03：文-图生成训练缺少图像数据、结构策略及监控的专属能力

- **条款号**：`1.3.2.5.1.4.3.1.2`—`.3.1.5`、`.3.4.1`—`.3.4.5`。
- **证据**：
  - 上传校验只按扩展名统一判断，未验证图像文件有效性、图文配对关系，也未显示图像数量、尺寸/分辨率等统计。
  - 训练页没有文-图模型结构高级参数、训练阶段、优化器与损失函数组合的专属联动。
  - 监控页只有两条通用“训练/验证”曲线，没有总损失、对齐损失、重建损失，也没有每 500 步生成样例。
  - 日志缺少级别/关键字筛选；无训练时长、平均步耗时、错误频次分析；无可编辑告警阈值和邮件/系统通知渠道。
- **整改建议**：实现图文对上传/预览/异常样本统计、损失组合配置、三类损失曲线、样例画廊、日志分析及告警规则编辑。

### P1-04：分布式训练拓扑不可编辑，多范式并行能力组主体缺失

- **条款号**：`1.3.2.5.1.4.4.1.1#1`—`.1.3#3`、`.4.2.1`—`.4.2.4`。
- **证据**：
  - 拓扑节点没有拖拽能力，页面中可拖拽节点数实测为 0；“智能生成拓扑”只显示 Toast，不改变节点或连线。
  - 通信配置缺少带宽优先级；聚合频率不能动态调整；无时间范围、缩放、节点排序。
  - “多范式并行训练支持”复用了同一拓扑页，页面未出现数据并行、模型并行、流水线并行、张量并行选择。
  - 无流水线层划分、微批次数、张量行/列切分、可读配置预览及资源冲突错误/修复建议。
- **整改建议**：实现可拖拽拓扑和可观察效率变化；增加并行范式组合器、动态参数面板、配置预览及带错误定位的有效性校验。

### P1-05：有监督微调缺少多阶段训练、Gang Scheduling 与 GPU 调度闭环

- **条款号**：`1.3.2.5.1.4.5.1.1`—`.5.1.7`、`.5.2.1`—`.5.2.5`、`.5.3.1`—`.5.3.2`。
- **证据**：
  - 核心页只有模型、LoRA/QLoRA/P-Tuning 选择和通用训练参数；无 LoRA rank/alpha 动态参数、智能范围提示、梯度冻结/层级微调/小样本配置。
  - 无可新增、排序、设置依赖的多任务/多阶段列表，也无中间结果、可自定义指标、最终性能/时间/资源报告。
  - 分布式页为通用拓扑，没有节点数、每节点 GPU 数、NCCL/Gloo 推荐、Volcano Gang Scheduling 开关/超时/重试。
  - 无队列 ETA、暂停/恢复/取消/优先级/重试；GPU 页没有每卡利用率、显存、温度、功耗、通信带宽和非最优路径告警。
- **整改建议**：建立微调专属向导、多阶段依赖编排、Gang 调度队列和 HAMi GPU 拓扑/逐卡监控，所有队列操作应产生真实状态变化。

### P1-06：强化学习可视化与任务 API 仅部分实现

- **条款号**：`1.3.2.5.1.4.6.1.2#1`—`#3`、`.6.2.1#1`—`.6.2.2#3`、`.6.3.1#1`—`.6.3.2#3`。
- **证据**：
  - 算法切换不会动态替换参数表单；模板保存/重命名/删除仅 Toast，没有模板列表状态。
  - 可视化页无并行任务选择、历史训练记录、时间范围、缩放/悬浮数据点和多任务同尺度切换。
  - API 页只有 3 个通用端点和一段 cURL；未完整呈现创建参数、暂停/恢复/停止、状态/指标/日志查询、错误码与异常处理，缺少 Python/Java 实例下载或切换。
- **整改建议**：按算法维护动态 Schema；实现可复用模板数据；补齐历史与多任务图表交互；建立完整生命周期 API 目录、在线调试、响应错误和多语言代码示例。

### P1-07：模型测评中的多类型测评和自动化报告页面语义错配

- **条款号**：`1.3.2.5.1.4.7.1.1#1`—`.7.1.3#3`、`.7.3.1#1`—`.7.3.3#2`、`.7.6.1#1`—`.7.6.3#3`。
- **证据**：
  - “多类型模型测评”主体是训练架构、学习率、批次、轮次表单，未提供语言/多模态类型切换、多模态模型与任务选择、模型版本、测评参数及执行监控。
  - “自动化报告与可视化”主体是训练损失/GPU/日志监控，没有综合报告结构、指标看板、柱状图/雷达图/混淆矩阵、指标分解、数据导出。
  - 流程阶段标记为 `draggable`，但没有拖拽事件；无新增/删除/跳过阶段、阶段配置抽屉、方案列表及编辑/删除。
  - 右侧 60 个细分标签可以打开原文，但大部分不能定位到对应真实控件。
- **整改建议**：分别建立“测评任务向导”“执行监控”“报告中心”；实现模型类型联动、报告钻取和导出；完成流程设计器拖拽/增删/依赖校验及方案 CRUD。

### P1-08：推理引擎缺少模型资产、交付实例和服务运营的可操作详情

- **条款号**：`1.3.2.5.1.4.8.1.1#1`—`.8.1.4#3`、`.8.2.1#1`—`.8.2.5#3`、`.8.3.1#1`—`.8.3.3#3`。
- **证据**：
  - 模型分类、资产登记、体验日志、用量分析按钮只显示 Toast；筛选按钮不改变模型结果；没有元数据编辑表单、版本状态切换、日志列表/详情、调用排行趋势。
  - 多模型体验只显示一个 Qwen 输出区，不符合 2—4 个模型结果并排展示。
  - 交付页没有压缩/转换/测评任务状态和日志，步骤按钮只显示 Toast；没有服务实例表、访问地址、启动/停止/滚动升级/回滚。
  - 实测交付页无告警阈值输入项，无服务实例管理表；“查看 P50/P95/P99 与日志”只显示提示。
  - 服务编排是静态流程；没有异步开关、回调 URL、实例列表和执行历史。运营分析、审计日志、健康度均只通过固定数字/Toast 表达。
- **整改建议**：把三类能力拆成模型资产、交付流水线、实例管理、服务网关、编排实例、运营分析等专属子视图；实现 CRUD、状态机、过滤、版本切换、回滚和日志详情。

### P1-09：文档与导出物格式不符合条款

- **条款号**：`1.3.2.5.1.4.1.6`、`.2.6`、`.3.5`、`.4.3`、`.5.6`、`.6.3.2`、`.7.7`。

  - 示例代码缺少 Jupyter Notebook/示例项目下载；未覆盖要求的 Python、cURL、Java 切换。

## 五、P2 问题

### P2-01：矩阵缺少系统概述与功能架构的独立追溯行，状态字段过早判定

- **条款号**：`1.3.2.5.1.1 系统概述`、`1.3.2.5.1.2 业务流程`、`1.3.2.5.1.3 功能架构`。
- **证据**：矩阵列出 6 条业务流程和八大模块功能条目，但没有系统概述、交互式端到端生产、单机到千卡、故障恢复、多模态支持等概述性约束的独立验收行；所有行均提前标记“已覆盖（待交叉审核）”。
- **整改建议**：补充非功能/总体能力条款，定义可验证的原型证据；状态改为“已验证 / 部分覆盖 / 未覆盖”，由自动化结果或复审结论驱动。

### P2-02：交互处理存在重复分支和若干表面控件

- **条款号**：影响全局交互可信度，代表页面为模型库、文档中心、测评流程设计器。
- **证据**：`genericAction` 中 `tryApi` 分支重复；模型库局部搜索框没有事件处理；流程节点设置 `draggable` 但没有拖拽逻辑；多个操作统一返回固定成功 Toast。
- **整改建议**：清理重复分支；为所有可见按钮、筛选框、拖拽元素建立可测试的状态更新；禁止无状态变化的“成功”反馈。

## 六、通过项

1. **范围控制通过**：主导航和原型正文未实现 `1.3.2.5.2 超大规模预训练模型` 或 `1.3.2.5.3 大模型算法服务`；推理引擎内的“模型服务应用”属于 `1.3.2.5.1.4.8.3`，不是越界。
